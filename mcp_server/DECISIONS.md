# Decisions and assumptions (one line each: what, why)

- Installed `mcp` 1.30.0 (pinned `<2`): the prompt requires `mcp.server.fastmcp.FastMCP`, which mcp 2.x removed (renamed `MCPServer`); pip's default install was 2.3.0.
- SDK 1.30.0 supports: `ToolAnnotations` (yes), `Context.report_progress` (yes), resource templates and prompts (yes: `@mcp.resource`, `@mcp.prompt`, `list_resource_templates`). Prompts 2/3 can rely on all four.
- `FRONTEND_DEVELOPMENT_GUIDE.md` and the PRD do not exist in the repo, so "in guide" statuses in ENDPOINTS.md are judged from `docs/API_CONTRACT.md` and the code; the code is the source of truth.
- The backend was not running during discovery, so `/openapi.json` was not fetched; ENDPOINTS.md is from reading the routers.
- Auth: the backend accepts `Authorization: Bearer` (JWT or `kw_live_...`) and cookies named `auth_token` etc., not `session_id`. Token mode sends Bearer only; login mode stores the JWT returned by `/auth/login` and sends it as Bearer (the cookie jar is also kept).
- API tokens made with the default scopes (`read`,`write`) get 403 on project/run routes because the backend checks `runs:read` etc.; documented in ENDPOINTS.md, the token must be created with the four `runs:*` / `tests:*` scopes.
- Guest mode only works when the backend runs `ENV=dev` with `ALLOW_SYSTEM_USER_FALLBACK=true`; otherwise protected calls fail with the standard auth error.
- `/targets/check` does not actually probe the URL; `reachable` is true for any well-formed URL. The MCP surfaces the backend's answer as-is rather than adding its own probe (an own probe could itself be an SSRF vector).
- `check_target` verdict mapping: allowed=false+reachable=false means a malformed URL ("Invalid target URL"); allowed=false otherwise is "Blocked by SSRF policy"; reachable=false is "Unreachable, is the app running?".
- Backend run objects have no `progress{step,done,total}` or `error` field. `get_run` reports `progress{stage,percent,step}` with `step` filled best-effort from `/runs/{id}/execution`; the failure reason is not available from the run object.
- `resume_run`/`retry_run` check the stage client-side because the backend does not enforce stage (no 409s); `retry_run` is limited to failed/cancelled runs.
- The backend does not apply stored project credentials when creating a run, and the password cannot be read back, so `start_run(project_id=...)` cannot use them; callers pass `username`/`password` explicitly. `set_project_credentials` and `start_run` say so.
- `start_run.review_mode` defaults to `None` meaning "project's default mode, else manual" (instead of a literal `"manual"`), so a project's autonomous default is honoured.
- Budget validation: keys `max_pages`, `max_steps_per_test`, `max_run_minutes`, `parallel_workers` are range-checked against `/config/defaults` limits; `explore_seconds`, `max_tests`, `test_timeout_ms` (read by `POST /runs`) must be positive ints; other keys are rejected.
- `get_project_credentials.updated_at` is always null: the backend returns only `{hasSecret, username}`.
- `create_project` does not accept a GitHub PAT parameter (secret handling for it is out of scope); `github_url` is accepted. A PAT can still be set from the web UI.
- There is no project-overview route; `get_project_overview` is composed client-side from project + runs + saved tests.
- Commit analysis / suggest-fix / auto-fix routes exist but are left for prompts 2-3 (workflow tools).
- `get_stats` is global in the backend (not per-user); the tool docstring says so.
- Secrets are scrubbed from error text via a registry (`errors.add_secret`) that holds the configured password/token, login JWT and any password passed to a tool; nothing secret is ever logged (debug logs contain method, path and status only).
- Tool outputs: URLs under keys ending in `url` are made absolute; payloads over 20,000 chars have long strings trimmed with `[truncated N chars]`.
- `--check` writes its report to stdout (it is a CLI mode, never the protocol channel); the server code path never writes to stdout except through the MCP transport.
- Smoke test against a live backend was not run: no backend was running and starting it would have meant registering an account in the user's real `data/kawach.db`.

## Prompt 2 decisions

- Resources: SDK 1.30.0 supports resources and resource templates; registered `kawach://projects` plus four `kawach://runs/{run_id}/...` templates (report, catalog, bugs, app-map). They reuse the tool functions, so output rules are identical.
- Review route takes ONE decision per call (`{test_ids, decision: approved|rejected, reason}`), not a mixed list, and has no `resume` flag. `review_tests` therefore sends rejections first and approvals last (up to 2 POSTs) and then reads the stage.
- The backend auto-starts execution after ANY review call whenever at least one catalog test is approved (even a pure rejection call). To avoid surprise starts, `review_tests` refuses unless `resume=True` when any test would remain approved, and refuses `resume=True` when none would. `reject_tests` refuses when other tests are already approved. `approve_all_and_resume` sends no `resume` field (the backend ignores unknown keys).
- Catalog route returns frontend-shaped tests: no `category`, no `pagePath`, steps are plain strings, and `review_status` uses `pending` (mapped to `proposed`). `category`/`pagePath` are always null; a category filter is ignored with a note.
- `PATCH /catalog/{id}` cannot change status, so `update_test(status=...)` goes through the review route (approve/reject; rejecting needs a `reason`; a test cannot be moved back to `proposed`). `steps` is a list of strings; `description` maps to `expected_result`.
- `POST /catalog/test` takes only `{prompt}` and the LLM writes the test. `add_test` validates the structured arguments (>=2 steps, non-empty actions), turns them into a numbered prompt and returns the id the backend generated. The steps guide the generator; they are not copied verbatim.
- Bug status is re-derived from the replays: confirmed only with 3 finished replays all reproduced, flaky for 1-2, not_reproduced for 0. A backend label that disagrees is overridden with a `status_note`; "confirmed" without 3 finished replays becomes `unverified`. Reason: the backend mapper fabricates placeholder replays (fixed durations such as 1200ms) when `verification/<bug>.json` is missing, so its label cannot be trusted alone.
- `summary.total` in `list_bugs` = confirmed + flaky + unverified (not_reproduced excluded, as the product law says); `by_severity` counts confirmed bugs only.
- `GET /bugs/{bug_id}` does not need a run id; bug `category`/`assertion type` are not reported, so timelines read `Trial 2: reproduced 1420ms` without assertion names. `testId` is parsed from the repro script URL. `playwright_code` is fetched best-effort from that URL.
- `GET /runs/{id}/logs` returns the whole log (backend keeps the last 500) with no paging parameters, so `get_logs` pages client-side. `tail=True` shows the newest `limit` lines after skipping `offset` newest ones.
- SSE frames carry only `data: {json}` with a `type` field (no `event:` lines). The parser supports both. Mapping: `run.status`->stage_changes, `test.update`->tests, `worker.update`->workers, `budget.update`->budget, `catalog.ready`, `run.done`. The stream first replays existing log history, so with a small `max_events` the result may be only history.
- Run objects carry only a progress percentage, so `wait_for_run` reports `report_progress(progress=percent, total=100)`; step text comes from `/execution` (best effort).
- `wait_for_run` also returns (with a `note`) if the run reaches a terminal stage that is not in `until_stages`, otherwise it would wait for something that can never happen. Transient failures (unreachable, 5xx) are retried 3 times with 0.5s/1s backoff; 404 fails immediately.
- Reports: `GET /runs/{id}/report` is a structured JSON object, not markdown. `get_report` reads `files/report.md` and falls back to a JSON summary while that file does not exist yet.
- Exports: the backend has no catalog export, no markdown-report export and no full-archive route. `export_catalog` builds JSON/CSV from the catalog API; `export_report_markdown` downloads `files/report.md`; `export_run_archive` downloads `/runs/{id}/export`, which is the passing-tests Playwright project (or the whole run folder if nothing passed); `export_playwright_scripts` uses `/export/scripts`.
- `read_run_file` only reads root-level files of the run folder (plain names); the backend additionally refuses `secrets.json` and `input.json`.
- Filesystem: names pass `[A-Za-z0-9._-]` sanitising (leading dots stripped, 100 char cap); results are checked with `resolve().is_relative_to`; unique suffixes `_1`, `_2` prevent overwrites; zip extraction validates every entry before writing anything, rejects absolute paths, `..`, drive letters and symlinks, and caps the total at 200 MB.
- `download_artifact` accepts only the configured backend host; a bare id maps to `/artifacts/{id}`.
- `get_app_map` combines `/app-map` (pages, forms, interactive counts) with `files/app_map.json` (summary text, features) when available; `buttons/links` detail per page is not in the API so `full` shows each page's discovered `actions`.
- Smoke read-only pass against a live backend was not run (backend not running; same reason as prompt 1).

## Prompt 3 step 0: fixes from the first live run

Ran against a LIVE backend instance (the real KAWACH code on an isolated temp DB/storage, stub LLM, example target app on :4000), not the user's own data.

- Auth confirmed live: `POST /auth/login` returns a JWT; the client sends `Authorization: Bearer <jwt>` and re-logs-in on 401 (re-login itself covered by mocks only, not forced live).
- **Bug replays from the API are fabricated.** `GET /bugs/{id}` returned three `1200ms` "reproduced" replays for every confirmed bug, while the real record in `verification/<bug>.json` had attempts of 420/410/395ms. The mapper swallows a load error and fabricates replays from the label. Fix: replays now come only from `GET /runs/{id}/files/verification/{bug}.json`; a bug without that record (or with fewer than 3 finished attempts) is `unverified`, never confirmed, and listed separately. All later workflow tools must use `bugs.load_bugs` / `bugs.norm_bug`.
- **`POST /runs/{id}/review` executes the whole pipeline inside the request** (about 18 s here) and returns after the run is `done`. A review call can therefore exceed the client timeout. Fix: review POSTs use a 25 s timeout and a timeout is reported as "submitted, still running" (verified live that the backend keeps going after the client stops waiting; stage was `verifying` right after the timeout and `done` later). Timeouts now carry `kind="timeout"` (same message as unreachable) and are retried by `wait_for_run`; `health_check` reports them as `unreachable`.
- There is no separate resume step after review in this backend; hints in `start_run`, `get_run` and `resume_run` now say so. `resume_run` is documented as a low-level override that records no approvals.
- Observed, not changed: run counts can exceed planned tests (13 results for 11 planned because exploratory tests are included), so `get_metrics` pass rate is over executed tests. `stage_changes` from the stream use the frontend status names (`completed` for `done`).

## Prompt 3 decisions

- Server name is `kawach-qa` (version = package version, set on the low-level server). Startup runs a health probe (5 s cap, never raises) and logs version, base URL, auth mode, download dir and result to stderr.
- `--check` prints a human report and exits 0 only when the backend answers AND login works; a wrong password is reported, not a traceback. `/health` is called with `auth=False`, so it never logs in (found live: a wrong password used to crash `--check`).
- Unexpected exceptions become `Unexpected error in <tool>: <ExceptionType>` (no message text, so nothing sensitive can leak); the traceback goes to stderr only.
- Workflow tools take bug truth only from `bugs.load_bugs`/`norm_bug` (real verification record). `get_bug` gained an optional `run_id` because bug ids such as `B01` exist in every run and the global `GET /bugs/{id}` returns the first run that has that id. `get_bug_fix_context` and `save_repro_script` always read the run-scoped bug list.
- `get_run_summary.progress` is `{stage, percent, step, done:null, total:null}`: the API has a percentage, not step counts. `metrics.total_tests` is the executed count (passed + failed + errored) so the numbers add up; planned tests are fewer when exploratory tests also run.
- `get_bug_fix_context` page path: bug steps ("Navigate to /x"), then the `page.goto` in the repro script, then any `/path` token, then the app map (a page whose last segment appears in the title/steps); otherwise it says the path was not recorded. `category`/`pagePath` do not exist in the catalog, and `errorMessage` comes from the raw `files/bugs.json`.
- `save_repro_script`: destination must resolve inside the server's working directory (absolute paths inside it are fine); collisions become `name_1.spec.ts` unless `overwrite=true`. The saved script imports `../../../apps/runner/fixtures`; the tool returns a `note` saying to adapt it.
- `retest_after_fix` recovers target URL, project, prompt and `max_pages` from the previous run. The spec text and app credentials cannot be read back from the API (`input.json` is refused), so if the previous catalog has spec references it requires `spec_file_path`/`spec_id` or `allow_default_spec=true` and starts nothing otherwise. Default mode autonomous.
- `compare_runs` matches by `(testId, normalised title)` first, then by title alone (reported in `matching_note`); only confirmed bugs count as fixed/new/persisting; a bug "fixed" but flaky in the new run says `now: flaky`.
- Regression workflow wraps `POST /projects/{id}/saved-tests/run-all` (via `run_saved_tests`) and `GET /runs/{id}/tests` for per-test errors.
- Prompts follow the real backend: rejections first, then approvals; no separate resume step after review; `add_test` is prompt-driven.
- e2e Scenario B: `review_tests` rejects one test (no approvals, so no execution starts), then `approve_all_and_resume` approves the rest, because approving first would start the run before the second review call. The scenario's "one approve and one reject" in a single call is exercised in the mocked tests.
- e2e live finding (stub mode): a test that was REJECTED in `catalog.json` was still executed and reported (`results.json` lists it as passed), and `review_log.json` kept only the last review call's decisions (the earlier rejection is missing from `get_review_log`). The e2e step "rejected test was not executed" therefore FAILs against this backend; it is a backend behaviour, not an MCP defect. Not verified with a real (non-stub) LLM/runner.
- Antigravity's own `mcp_config.json` was not read or edited (it is user configuration and may hold other servers/secrets); the README tells the user to merge via the "View raw config" button.
