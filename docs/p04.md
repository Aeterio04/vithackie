## Phase 1: Parallel build

### Description

Four tracks build at the same time against the contracts, from 00:20 to 02:30. Each track must work on its own by the end.

This is where the work gets divided so that nobody blocks anybody. The trick is that every track has something to build against that **already exists** from Phase 0:

- Track D builds the whole UI against the sample JSON in `contracts/samples/` (no backend needed).
- Track C builds the runner against a hand-written test and, once Track A merges, the demo app.
- Track B builds agents against the typed stubs and the `fake` LLM provider, then the real LLM.
- Track A builds the demo app that everyone else will test against. It is the smallest piece and the earliest to finish, so its owner can then help B or C (see the rebalancing note under Track A).

| Track | Owns | Needs from others | Produces for others |
| --- | --- | --- | --- |
| A | `target-app/` | nothing | The app the explorer, runner and benchmark use; `spec.md`; `ground_truth.json` |
| B | `llm.py`, `prompts*`, `agents/`, `graphs/`, `fake_llm/`, `runner/explore.ts` | `runner_client.list_tests` (from C), Playwright config (from C) | App map, catalog, scripts, bug write-ups, the two graphs, `STUB_MODE` |
| C | `runner/` (except `explore.ts`), `runner_client.py`, `verifier.py`, `report.py`, `main.py` | Agent functions (from B) only at stitching time | Runner, evidence, triage, verifier, API, report |
| D | `frontend/` | nothing (uses samples) | The UI |

**Exit:** each track works alone. The runner runs a hand-written spec against the target app. The explorer prints an app map. The UI renders mock data.

### Track A: Target app and ground truth

#### Description

The demo needs an app to test, and we need to know exactly which bugs are inside it, otherwise we cannot say how many our AI finds. Track A builds a tiny web app with a signup, login, dashboard, settings and logout, plants nine known bugs in it, and writes down the correct behaviour (the spec) and the list of planted bugs (the ground truth). The benchmark in Phase 4 compares what the AI reports against this list to compute **recall** (how many planted bugs were found) and **precision** (how many reported bugs were real).

It also has a switch, `BUGS_OFF`, that turns bugs off. Running the full pipeline against the clean version is the cheapest way to measure false positives.

About 60 to 75 minutes with a coding agent, then Docker (Phase 3.6) and the benchmark (Phase 4). The agent itself needs about 25 minutes. Use the remaining time to review the app by hand.

> **Rebalancing.** Track B is the heaviest track. When Track A is done, its owner should take prompt B2 (the explorer) from Track B's list. They are independent.

#### Tasks

- **A1.** Build a tiny local web app with a coding agent: `/signup`, `/login`, `/dashboard` (add and delete items), `/settings` and `/logout`. Keep data in memory. Add `/__reset` to wipe state between runs.
- **A2.** Plant 8 to 10 bugs and write the spec sheet (`spec.md`) with the correct behavior for each. The nine bugs are in CONTRACTS section 10:
  - Signup accepts an invalid email.
  - Signup accepts a password shorter than the spec minimum.
  - Wrong password shows no error.
  - Login fails for emails with capital letters.
  - Dashboard accepts an empty item title.
  - Delete removes the wrong item.
  - Back button after logout still shows the dashboard.
  - `/settings` throws a console error.
  - One intermittent failure (every second save fails) to demo the "flaky" status.
- **A3.** Write `ground_truth.json` (id, description, spec ref) and seed one test user.

### Track B: Agents and graphs

#### Description

Track B builds the "brains": everything that talks to the LLM, plus the glue that runs the stages in order. There are six pieces. Think of it as an assembly line where each station takes a file in and puts a file out.

```
input.json + secrets.json
   │  B2 Explorer (crawler + 1 LLM call) ─────────────▶ app_map.json
   │  B3 Planner (1 LLM call) ────────────────────────▶ catalog.json
   │  (human edits, or Reviewer decides) ─────────────▶ catalog.json (approved)
   │  B4 Script writer (1 LLM call per test) ─────────▶ scripts/T01.spec.ts ...
   │  [Track C runs Playwright] ──────────────────────▶ results.json, bugs.json
   │  B6 Bug reporter (1 LLM call per bug) ───────────▶ bugs.json (filled in)
   │  [Track C verifies, builds report]
   └  B5 LangGraph wires all of it, and fakes it in STUB_MODE
```

B1 (`llm.py`) sits under all of them: it is the single place that calls the model, caches answers on disk, retries on errors, and counts tokens and cost.

**Order inside the track.** Run B1 first (about 20 minutes, everything else needs it). Then B2, B3, B4 and B6 are independent: run them in separate agent sessions on separate branches at the same time if you have the quota, or one after the other. B5 can start at the same time as B2 to B4, because it only needs the stub signatures from Phase 0.

#### Tasks

- **B1. `llm.py`.** JSON-mode output, retries, a disk cache keyed by prompt hash, and token and cost counters. The cache protects the live demo from rate limits and slow responses.
- **B2. Explorer.** `runner/explore.ts` logs in, then does a breadth-first crawl of same-origin pages. Limits are 10 pages and 90 seconds. Per page it records URL, title, headings, links, forms and fields (role, label, type), buttons, console errors and HTTP status. One LLM call turns this into an app map and context summary.
- **B3. Planner.** Input is the app map, prompt and spec. Output is 8 to 12 tests as JSON, each with id, title, description, specRef, priority and concrete steps with expected results. Rule in the prompt: one test per spec item.
- **B4. Script writer.** For each test, the LLM writes a Playwright `.spec.ts`. Rules in the prompt: role and text locators, unique data using `Date.now()` so parallel runs don't collide, assertions only from the spec's expected results, and no off-domain URLs. After writing, run `npx playwright test --list` to catch syntax and import errors. Retry once with the error fed back.
- **B5. LangGraph.** Build both graphs with stub nodes first, then fill them in. `graph.get_graph().draw_mermaid()` gives you the architecture diagram for the deck.
- **B6. Bug reporter (assigned in this edition).** For each bug candidate, one LLM call writes the title, category, severity, steps, expected and actual. (This was the "Repro report" step in the feature list; the first edition did not give it an owner.)

## llm.py
class LLM with:
- complete_json(*, system, prompt, schema_name, run_id=None, max_tokens=4000, temperature=0.2) -> dict | list
- complete_text(*, system, prompt, schema_name="text", run_id=None, max_tokens=2000, temperature=0.2) -> str
get_llm() returns a process-wide singleton. usage(run_id) -> LlmUsage reads runs/<id>/llm_usage.json (zeros if missing). Define `class LLMError(Exception)`.

Providers, chosen by settings.llm_provider:
- "anthropic": official `anthropic` SDK, messages.create(model=settings.llm_model, system=system, messages=[{"role":"user","content":prompt}], max_tokens, temperature). Join all text blocks. Tokens from response.usage.input_tokens / output_tokens.
- "openai": official `openai` SDK chat.completions.create with a system and a user message; for complete_json also pass response_format={"type":"json_object"}. If the API rejects `max_tokens`, use `max_completion_tokens` instead (handle both). Tokens from response.usage.
- "fake": no network. complete_json reads backend/app/fake_llm/<schema_name>.json and returns it; complete_text reads backend/app/fake_llm/<schema_name>.txt. If the file is missing raise LLMError(f"no fake response for {schema_name}"). Token counts = len(text)//4 for the response, len(prompt)//4 for the input.

JSON handling for complete_json: instruct nothing special in code (the caller's prompt asks for JSON), but parse defensively: strip ``` fences, take the substring from the first "{" or "[" to the last "}" or "]", json.loads. If parsing fails, make ONE repair call: same system prompt, user prompt = "Your previous reply was not valid JSON (<error>). Reply again with ONLY the valid JSON." and parse that. If it still fails raise LLMError with the first 300 characters of the reply.

Retries: up to 3 attempts per provider call with waits of 1s, 3s, 8s for rate limits, timeouts, connection errors and 5xx. Authentication or bad-request errors are NOT retried: raise LLMError with a clear human message (for example "Missing or invalid API key for provider anthropic").

Disk cache: directory backend/.llm_cache/. key = sha256 of json.dumps({provider, model, system, prompt, schema_name, temperature, max_tokens}, sort_keys=True). File <key>.json holds {text, inputTokens, outputTokens}. Modes from settings.llm_cache: "on" = read and write; "readonly" = read only (on a miss call the provider but do not write); "off" = neither. The fake provider never uses the cache. Cache the RAW reply text, so the JSON repair path is also cached.

Usage and cost: after every call (cache hit or not) add to runs/<run_id>/llm_usage.json (only when run_id is given) calls += 1, cacheHits += 1 on a cache hit, inputTokens, outputTokens, costUsd += in*price_in/1e6 + out*price_out/1e6 using settings prices. IMPORTANT: a cache hit still counts its ORIGINAL tokens and cost, so the report shows what a fresh run costs; cacheHits shows how many were free this time. Updates must be thread-safe (a lock) and atomic (temp file + replace).

## prompts.py
- load_prompt(name, **vars) -> str: reads backend/app/prompts/<name>.md, replaces every {{var}} with str(value). Raise KeyError naming the placeholder if any {{...}} is left unreplaced or if a var was passed that the template never uses.
- untrusted(text, label) -> str: returns '<untrusted_content label="{label}">\n{text}\n</untrusted_content>' after replacing any occurrence of "</untrusted_content>" inside text with "[removed]" and any "<untrusted_content" with "[removed]".
- guard() -> str: contents of prompts/_guard.md.
