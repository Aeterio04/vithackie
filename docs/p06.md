### Track C: Runner, verifier, API

#### Description

Track C builds everything that touches the browser during a test run and everything that serves results to the UI. It is the "engine room", and it is where the product's credibility comes from: if the evidence is missing or the verifier is wrong, nothing else matters.

The key idea is a strict **separation of bug from mistake**. When an AI writes a test script, the script itself can be wrong (bad locator, wrong URL). A wrong script must never be reported as an app bug. So Track C classifies every failure: an `expect()` mismatch is a bug candidate; everything else is a "test error". Then the verifier replays each candidate three times with no retries, and only a failure that happens again with the same signature counts as reproduced.

```
runs/<id>/scripts/*.spec.ts
        │  C1 Playwright project (config + fixtures)
        ▼
   C2 runner wrapper ── results.json, evidence/, bugs.json (candidates)
        │
        ▼
   C3 verifier ── verification/B01.json … and bug status
        │
   C4 FastAPI serves everything     C5 report.md + metrics.json
```

**Order inside the track.** C1 first (about 25 minutes). Then C2 (its `run_playwright` and `list_tests` functions must be pushed within 30 minutes of starting, because Track B's script writer calls `list_tests`). C3, C4 and C5 can then run in parallel, on separate branches.

#### Tasks

- **C1. Playwright project.** Config sets trace, video and screenshot to retain on failure, a JSON reporter, and a configurable worker count. `fixtures.ts` records console errors and failed or 4xx/5xx requests as attachments. It also routes all off-domain requests to abort and logs them, which is the allowlist.
- **C2. Runner wrapper (Python).** Runs the specs and parses the JSON report. An `expect()` mismatch becomes a bug candidate. Locator timeouts or script crashes go into a separate "test error" bucket, not the bug list. This is the cheapest precision guard.
- **C3. Verifier.** For each candidate, replay 3 times with `--retries=0 --workers=1` and compare error messages. 3/3 is confirmed, 1/3 or 2/3 is flaky, 0/3 is not reproduced. No LLM.
- **C4. FastAPI.** Endpoints from the Architecture section. Each run is a folder plus `run.json`. Pipelines run as background tasks that update `stage` as they go.
- **C5. Report generator.** Markdown from `run.json`: summary, bug table with statuses, coverage (pages and forms exercised), tests passed, failed and errored, wall-clock time, tokens and cost.
