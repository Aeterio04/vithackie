## Phase 2: Stitching

### Description

From 02:30 to 04:00 the four tracks are joined, and the first full run must work by 03:30, even if it is ugly.

This is where most hackathon projects stumble, because every track "works" alone and nothing works together. The defence is to join the pieces in a fixed order, from the outside in, and to always have something runnable:

1. First connect the UI to the real API while the backend still runs in `STUB_MODE`. This isolates UI-to-API bugs from agent bugs.
2. Then replace stub stages with real stages one graph at a time (graph 1, then graph 2), each tested on the real demo app.
3. Then do one complete run and fix what breaks, ordered by how much it would hurt the demo.
4. Only then tune prompts, using numbers (how many scripts crash, how many planted bugs were found), not feelings.

Who does what: the owner of Track D does 2.1. The owners of B and C pair on 2.2 and 2.3 (B knows the agents, C knows the runner and API). Everybody joins 2.4. The owner of Track A joins 2.5 because they know which bugs should appear.

**Ownership rule for Phase 2 prompts.** The integration agents may edit files owned by any track, because that is the whole point of stitching. Rules: make the **smallest** change that fixes the problem, one commit per fix with the owning track in the message (for example `fix(track-c): ...`), and list every touched file in the final report. Never change `docs/CONTRACTS.md`; if a contract is wrong, say so under CONTRACT CHANGE NEEDED and let the humans decide.

### Tasks

- **2.1** The frontend swaps mocks for the real API.
- **2.2** Wire graph 1 to the API and run it on the target app. Check that the catalog is sensible.
- **2.3** Wire graph 2: scripts, run, triage, verify, report.
- **2.4** Do the first full end-to-end run by 03:30. List what broke and fix it in order of demo impact.
- **2.5** Tune prompts until these hold:
  - Most generated scripts run without script errors.
  - At least 5 planted bugs show up as confirmed.
  - False positives are few.

**Exit:** one click on the UI produces a report with at least one confirmed bug and one flaky bug.

### Prompt 2.5: Tuning with numbers

Branch: `phase2/tuning`. Expected time: 45 to 60 minutes (until 04:00).

````text
You are the PROMPT TUNER of an AI QA tool. The pipeline works end to end. Now we improve quality with NUMBERS, not impressions. The three goals: (1) most generated scripts run without script errors, (2) at least 5 of the 9 planted bugs show up as confirmed, (3) very few false positives (reported bugs that are not planted bugs). You only change prompt templates in backend/app/prompts/*.md and small validation rules in the agents; no architecture changes.

FIRST: read docs/CONTRACTS.md and docs/AGENT_RULES.md completely, docs/E2E_LOG.md and target-app/ground_truth.json. Work on branch phase2/tuning.

## Step 1: a scoring script (you own backend/scripts/score_run.py)
`python backend/scripts/score_run.py <run_id> [--ground-truth target-app/ground_truth.json]` reads the run folder and prints:
- Scripts: number of tests approved, scripts ok, scripts error; of the executed tests: passed, assertion_failure, test_error (with the first line of each test error).
- Bugs: for each bug (id, status, title, testId, specRef) a SUGGESTED ground-truth match: a bug matches a planted bug when their specRef sets intersect AND it is an assertion failure; if one spec item has two planted bugs (S10 has GT08 and GT09) match by keywords in the bug title/actual ("console", "uncaught", "preferences" -> GT08; "saved", "save", "500" -> GT09). Print the suggested table, then: true positives (distinct planted bugs matched, counting confirmed AND flaky), missed planted bugs (ids and descriptions), unmatched bugs (possible false positives), recall = TP/9, precision = matched bugs / all bugs, replay rate = reproduced attempts / total attempts over all bugs.
- Also print the same three numbers restricted to confirmed bugs.
This script is a quick guide; the final benchmark in Phase 4 is matched by hand.

## Step 2: baseline
Run 3 full runs: `python backend/scripts/run_e2e.py --mode manual --approve-all --reset-target`, score each. Record the baseline in docs/TUNING_NOTES.md as a table (run id, scripts ok/error, test errors, recall, precision).

## Step 3: tune in this order, one change at a time, re-measuring after each
A. If test errors (script mistakes) > 2 of 11: read each test error and its script. Typical causes: wrong label text (script writer invented "Submit" instead of "Sign up"), missing exact: true, expecting a redirect that the spec does not state, using the seeded user for a test that mutates data, not waiting for navigation. Fix backend/app/prompts/script_writer.md (add a rule or a corrected example) or planner.md (make steps use exact labels). Do not hard-code demo-app specifics into the prompts: rules must be general (for example "copy button and label texts exactly from the app map"). 
B. If a planted bug is MISSED: find out where it was lost. Not planned (add planner rule: one test per spec item and the expected result must be asserted)? Planned but the script did not assert it? Asserted but passed because the script was too lenient (for example it accepted either outcome)? Fix the responsible prompt in a GENERAL way (for example "assert the exact message text from the spec").
C. If a FALSE POSITIVE appears: read the script and the error. Is the assertion unrelated to the spec? Is the locator ambiguous (matches two elements, strict mode violation is a test error, but a wrong `toHaveText` is not)? Fix the prompt, or add a code-side guard in script_writer.py (for example reject scripts with assertions on text that is not in the spec or the app map).
D. The intermittent bug (settings save): confirm that a test saving settings exists; document in TUNING_NOTES.md how often it shows as flaky (it depends on counter parity).
E. Stop when: test errors <= 2 of 11, recall >= 5/9 confirmed (aim for 7+), false positives <= 1, in 2 of 3 consecutive runs. Do not overfit the prompts to the demo app wording.

## Step 4: stability
Run 3 more times with the final prompts. Record the results. Warm the LLM cache by running the exact demo input once more (the one the team will type on stage): note in docs/TUNING_NOTES.md the exact prompt and spec that were used so the live demo hits the cache.

## Check it yourself
1. docs/TUNING_NOTES.md has a baseline table, one row per change (what changed, before/after numbers), and the final table of 3 runs.
2. `python backend/scripts/score_run.py <run_id>` works on every run and its numbers agree with a manual look at bugs.json for one run.
3. `git diff main -- backend/app/prompts` shows only general rules (no demo-app specific selectors or strings other than examples).

Finish with the final message format from docs/AGENT_RULES.md section 9.
````
