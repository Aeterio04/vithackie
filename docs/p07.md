### Track D: Frontend

#### Description

Track D builds the face of the product: the screens a judge will actually look at for five minutes. It is built **entirely against the sample JSON from Phase 0**, with a built-in mock mode that simulates a whole run (stages moving, a catalog to edit, bugs with evidence), so Track D never waits for the backend. At stitching time (Phase 2.1) one environment variable flips it from mock to real.

What the UI must make obvious, in order of demo value:

1. **The stage stepper** moving (it shows the system is alive and autonomous).
2. **The catalog** that the human can edit, with "add by prompt" (it shows human-in-the-loop).
3. **A bug card** with evidence: screenshot, a playable video, expected vs actual, a replay badge such as "3/3 confirmed" or "2/3 flaky", and the runnable `.ts` script (it shows trust and reproducibility).
4. **The report and metrics** (it shows numbers, which is what the PS asked for).

**Design notes.** Plain React + Vite, polling every 2 seconds, no websockets, no UI framework, plain CSS with variables. Use a dark background with a green accent so the UI matches the pitch deck. Everything from the app under test is rendered as text, never as HTML (NFR-7).

| Prompt | Branch | Files it owns |
| --- | --- | --- |
| D-1 (D1, D2, runs list) | `track-d/scaffold-form` | `frontend/` scaffold, `src/types.ts`, `src/api.ts`, `src/mock/**`, `NewRunPage`, `RunsPage`, theme |
| D-2 (D3, D4) | `track-d/run-page` | `RunPage`, stepper, polling hook, App map tab, Catalog tab |
| D-3 (D5, D6) | `track-d/bugs-report` | Bugs tab, Report tab, Metrics tab |

Run D-1 first. D-2 and D-3 can then run at the same time on separate branches (they touch different files; D-2 creates `RunPage.tsx` with empty placeholders for the Bugs, Report and Metrics tabs, and D-3 fills in those components, so merge D-2 first).

#### Tasks

- **D1.** Vite + React, `api.ts`, and mock data from the contracts.
- **D2.** New-run form: URL, prompt, spec, credentials and a mode toggle.
- **D3.** Run page with a stage stepper and polling.
- **D4.** Catalog table: edit, remove, an add-by-prompt box, and an "Approve and run" button.
- **D5.** Bug cards: severity, expected vs. actual, status badge with replay count (for example "2/3 flaky"), screenshot, a `<video>` tag as the replay viewer, script viewer, and trace download.
- **D6.** Report tab and metrics cards. Render everything as text, and use `react-markdown` without raw HTML. That covers NFR-7. Add a simple list of past runs.

## useRun(runId) hook
Returns {view, error, loading, refresh}. Fetches getRun immediately, then every 2000 ms while the stage is one of exploring, planning, scripting, running, verifying, reporting, created. It does NOT poll when the stage is done, failed or awaiting_review (but refresh() restarts polling, and the hook resumes polling automatically when a stage change makes it active again, for example after execute). Never overlap requests (skip a tick if one is in flight). Stop on unmount. Keep the previous view while a refresh is loading. On a fetch error keep the last view and expose the error (show a small "Connection lost, retrying..." banner and keep retrying every 2 s).
