## Overview

The goal is one thin pipeline that works end to end for the 9 am demo, not many half-built agents.

This plan assumes 4 people, about 9 hours (23:40 to 08:30), and a demo that runs on localhost. With 3 people, merge Track A into Track C. With 2, pair B with C and A with D.

Nothing is built yet. The plan cuts PRD v1.0 down to a proof of concept: a basic frontend, a basic backend, a basic agent structure, and the glue between them. Docker is added only if time allows. If you fall behind, cut in the order given under Cut order and risks.

### What the finished system does, in one paragraph

A QA engineer opens a web page and fills a form: the URL of the app under test, a background prompt ("this is a to-do app for small teams"), a spec sheet (numbered expected behaviours, `S1: …`, `S2: …`), a test username and password, and a mode (manual or autonomous). The system logs in and crawls the app within a budget to build an **app map**. A **planner** (an LLM) turns the app map, prompt and spec into a **catalog** of 8 to 12 tests, each linked to spec items. A human edits and approves the catalog (manual mode) or a **reviewer** agent does it and logs why (autonomous mode). A **script writer** (an LLM) writes one Playwright script per approved test. Playwright runs them with no LLM involved, and keeps a screenshot, video, trace, console log and network log for every failure. **Triage** separates real assertion failures (bug candidates) from broken scripts (test errors). A **bug reporter** (an LLM) writes a clear report for each bug. A **verifier** (no LLM) replays each bug three times and labels it confirmed (3/3), flaky (1/3 or 2/3) or not reproduced (0/3). Finally, the system produces a Markdown report with metrics. Everything is saved as plain files under `runs/<run_id>/`.

### How to use this document

1. Do Phase 0 first. Copy the **Shared contracts** section into `docs/CONTRACTS.md` and the **Agent rules** section into `docs/AGENT_RULES.md` by hand (about 3 minutes in total), then give the Phase 0 prompt to an agent. It builds the skeleton every other prompt depends on.
2. Every track has a description and a prompt in a code block. Paste the prompt as it is into a coding agent (Claude Code, Cursor, Codex). **One prompt, one agent session, one branch.** Do not combine two prompts in one session.
3. Every prompt starts by telling the agent to read `docs/CONTRACTS.md` and `docs/AGENT_RULES.md`. These are the single source of truth for file names, JSON shapes and function signatures. If you change something, change the file first and tell the team.
4. After each prompt, run its **Check it yourself** list. Do not start the next stage until the checks pass. If an agent's final message says "CONTRACT CHANGE NEEDED", resolve that before merging.
5. The prompts assume Python 3.11, Node 20, and a Linux or macOS shell. On Windows, use WSL.
6. **Merge rhythm.** Each person merges to `main` once per hour, after the checks for their last prompt pass and after pulling `main`. Never merge a branch whose checks fail.
7. **Cross-checking agent work.** An agent's own claim that "it works" is not evidence. Every prompt asks for a final report in a fixed format (Done / Not done / Deviations / How I verified). Read the "Deviations" line first. Then run the checks yourself.

### What is real and what is simplified

Say this honestly in the pitch. Judges trust a team that knows its own limits.

- **Explorer:** a crawler with a budget plus one LLM summary. It is not a free-roaming agent. This is deliberate: it cannot wander forever, which answers the "endless exploration" worry.
- **Test scripts:** the LLM writes one Playwright script per test. Playwright runs it, with no LLM at run time. This makes runs fast, cheap and repeatable.
- **Exploratory Tester:** rule-based edge-case probes, with no LLM.
- **Verifier:** no LLM, as in the PRD. A bug is only "confirmed" if the same assertion failure happens again, three times.
- **Sandbox:** Playwright route blocking (every request to a non-allowlisted host is aborted and logged), plus Docker if time allows. There is no VM sandbox.
- **Prompt-injection defence:** page content is treated as data (wrapped and labelled in every LLM prompt), the allowlist blocks off-domain requests even if an LLM is tricked, and scripts are produced by the LLM from the *spec*, not from page text. It is a layered mitigation, not a guarantee.

### Feature details

Each feature below says what goes in, how it works, what comes out, how it fails, and when it counts as done. File names and JSON shapes are defined in **Shared contracts**.

#### F1. Input form (FR-1)

- **Collects:** target URL, background prompt (optional but encouraged), spec sheet (required), test username, test password, mode (`manual` or `autonomous`).
- **Validates (backend is the authority; the UI mirrors the messages):**
  - URL parses and the scheme is `http` or `https`.
  - The host is on the allowlist (`ALLOWED_HOSTS`, default `localhost,127.0.0.1`). Otherwise error: "Host not allowed. This tool only tests staging or local apps."
  - The spec has at least one line that starts with `S<number>:`. Every non-empty line must start that way or be a continuation line indented by two spaces. A bad line gives an error naming the line number.
  - Mode is one of the two values.
- **On submit:** creates `runs/<run_id>/`, writes `input.json` (password excluded) and `secrets.json` (password only, git-ignored), writes `run.json` with stage `created`, starts graph 1 in the background, and returns the run id.
- **Failure:** validation errors return HTTP 422 with a list of `{field, message}`. The form shows them next to the fields.
- **Done when:** submitting creates a run folder and starts exploring. A bad URL or an empty spec shows an error.

#### F2. Explorer (FR-2)

- **Input:** base URL, credentials, budgets (10 pages, 90 seconds).
- **How it works:** a TypeScript Playwright script opens the base URL, finds a login form (a form containing a password field, on the page or at `/login`), fills the first text or email field with the username and the password field with the password, submits, and checks that the password field is gone. It then crawls **same-origin links only, breadth-first**. It visits pages; it never clicks buttons and never submits forms other than the login. It skips links whose text or URL looks destructive (`logout`, `signout`, `delete`, `remove`) and anything under `/__`. For each page it records URL, path, title, HTTP status, headings, links, buttons, forms with their fields (role, label, type, name, required), console errors, and whether the page needed login.
- **LLM step:** one call receives a compact version of the raw map (wrapped as untrusted content) plus the background prompt, and returns a short summary and a list of features with the pages that implement them.
- **Output:** `explore_raw.json` (crawler output) and `app_map.json` (raw plus summary and features).
- **Failure:** a crawler error never crashes the run. It writes whatever it found plus an `error` field. An LLM error writes the map with `summary: "(summary unavailable)"`.
- **Done when:** `app_map.json` lists every page of the target app and its forms, and the logged-in pages are marked `requiresAuth: true`.

#### F3. Planner (FR-3)

- **Input:** `app_map.json`, the background prompt, the parsed spec.
- **How it works:** one LLM call returns 8 to 12 tests as JSON. Rules enforced by the prompt: one test per spec item as a minimum, concrete steps, expected results taken from the spec (not invented), UI labels taken from the app map, each test independent of the others (creates its own data), tests ordered by priority.
- **Code-side validation:** the JSON must match the schema. Every spec ID must appear in at least one test's `specRef`. If some are missing, one retry names the missing IDs. If still missing, the code adds a simple fallback test for each missing spec item.
- **Output:** `catalog.json`.
- **Done when:** `catalog.json` is valid, and every spec item is linked to at least one test.

#### F4. Catalog review (FR-4, FR-5)

- **Manual mode:** the QA engineer sees the catalog as a table. They can edit a test's title, description, priority and steps, remove a test, add a test by typing a prompt (the planner turns the sentence into a complete test), and then press **Approve and run**. Removed tests are marked `rejected`, not deleted, so the report can say what was dropped.
- **Autonomous mode:** the Reviewer agent makes one LLM call per test and returns approve or reject plus a reason. It can **only** approve or reject. It cannot add or edit tests. The pipeline continues without a human.
- **Output:** the catalog with statuses updated, and `review_log.json` in autonomous mode.
- **Done when:** only approved tests move on. In autonomous mode `review_log.json` has a reason for every decision.

#### F5. Script writer (new, not in the PRD)

- **Input:** one approved test case, the app map, and the spec lines it references.
- **How it works:** one LLM call per test returns one Playwright `.spec.ts` file. Rules enforced by the prompt: the title starts with the test ID (`T05: …`); locators use roles, labels and text (never CSS paths); data is made unique with the `unique()` helper so parallel runs do not collide; assertions come only from the test's expected results; no off-domain URLs; credentials come from the `credentials` helper. After writing, the code runs `npx playwright test <file> --list`. If it fails, the error text is fed back to the LLM once for a fix.
- **Output:** `runs/<id>/scripts/<TestId>.spec.ts`, and `scriptStatus` on each test (`ok` or `error`).
- **Failure:** a script that still fails `--list` is kept but marked `error`. It is not run, and appears in the report as a test error.
- **Done when:** every approved test has a script that loads, or is marked as a test error.

#### F6. Runner and evidence (FR-8)

- **How it works:** a Python wrapper starts Playwright (Chromium) inside the TypeScript `runner/` project with environment variables for the base URL, script folder, worker count and output folder. A shared fixture records console errors, page errors and failed or 4xx/5xx requests for every test, and routes every request to a non-allowlisted host to `abort`, logging it. Playwright is configured to keep a trace, video and screenshot only when a test fails.
- **Output:** `results.json` plus `evidence/<TestId>/` for each failing test (`screenshot.png`, `video.webm`, `trace.zip`, `console.json`, `network.json`).
- **Done when:** every failed test has all five evidence files.

#### F7. Triage

- **How it works:** a failure is a **bug candidate** only if it is an assertion failure (an `expect()` mismatch). Locator timeouts, navigation errors, syntax errors and test timeouts are **test errors**. Candidates are de-duplicated by an error signature (the normalised error text with numbers and unique IDs removed).
- **Output:** `bugs.json` containing only assertion failures, each with `status: "candidate"`.
- **Why:** this is the cheapest precision guard. A script with a wrong locator should never become a "bug".
- **Done when:** `bugs.json` holds only assertion failures, and each test error is listed in `results.json` with its reason.

#### F8. Repro report (FR-9)

- **Input:** the bug candidate, its test case, the referenced spec lines, the error message and a console excerpt.
- **How it works:** one LLM call per bug returns a clear title, category, severity, numbered steps, expected result and actual result. The prompt forbids inventing facts that are not in the error output. The spec file itself is the runnable repro script.
- **Done when:** each bug has all fields and a script that runs with one command.

#### F9. Verifier (FR-10)

- **How it works:** no LLM. For each bug, run `npx playwright test <file> -g "<grep>" --retries=0 --workers=1` three times, one after another. A replay "reproduces" if the test fails with an assertion failure whose signature matches the original. 3 of 3 is **confirmed**, 1 or 2 is **flaky**, 0 is **not reproduced**.
- **Output:** `verification/<BugId>.json` per bug, and the bug's `status` and `replay` fields updated.
- **Done when:** one result file per bug, and statuses shown in the report.

#### F10. Report (FR-11)

- **Output:** `report.md` with a summary, bugs grouped by status with evidence links, a table of all tests, coverage (pages, forms and spec items exercised), timings, tokens and cost, parallel speedup, and blocked off-domain requests. `metrics.json` holds the same numbers for the UI cards.
- **Done when:** `report.md` opens in the UI.

#### F11. UI and API

- **Pages:** runs list, new run, and a run view with a stage stepper and tabs for app map, catalog, bugs, report and metrics. The UI polls every 2 seconds.
- **Done when:** a full run can be driven from the browser alone.

#### F12. Autonomous Reviewer (Should)

One LLM call per test returns approve or reject plus a reason. It cannot add tests. Reasons are visible in the UI. Done when every test in an autonomous run has a visible reason.

#### F13. Exploratory probes (Should)

Rule-based edge cases for every form in the app map: empty submit, a 300-character string, unicode and emoji, double-click submit, and a reload in the middle of the flow. Console errors, uncaught exceptions or 5xx responses become bug candidates with `source: "exploratory"`. No LLM. Done when probes find the settings console error without it being in the catalog.

#### F14. Export (Should)

Zips the passing tests with `fixtures.ts`, the config and a README so they run with `npx playwright test`. Done when the zip runs in a clean folder.

#### F15. Parallel run (Should)

Runs the catalog with 1 worker and with 4 workers and records both times. The speedup appears in the metrics. Done when `metrics.json` has both times.

#### F16. Safety (Should)

Refuses targets that are not on the allowlist, enforces budgets (pages, seconds, tests, per-test timeout), and logs blocked off-domain requests. Done when a non-allowlisted URL is rejected and blocked requests appear in the report.

## Decisions

Settle these in the first 10 minutes, with no debate. They answer PRD open questions 1, 3 and 4. Swap the stack if you must, but decide now.

| Area | Decision | Why |
| --- | --- | --- |
| Orchestrator | Python, FastAPI, LangGraph | Fast to write, easy for agents to generate, and LangGraph gives you a diagram for the deck. |
| Browser code | All in one TypeScript Playwright project (`runner/`). Python calls it through a subprocess. | One Playwright install, one browser set and one Docker image. |
| Frontend | React + Vite, polling every 2 seconds. No websockets. | Polling is trivially reliable. Websockets cost an hour and add failure modes. |
| Storage | Files on disk, `runs/<run_id>/`. No database. | Files are easy to inspect, zip, copy as a golden run, and diff. |
| LLM | One provider behind a single `llm.py`. Use whichever you have a key and quota for. | Provider swap is one env var. Disk cache protects the demo. |
| Credentials **(NEW)** | The password lives only in `runs/<id>/secrets.json` and is passed to Playwright as `TEST_PASSWORD`. Generated scripts read `credentials.username` and `credentials.password` from the fixtures, never literal values. | Secrets never appear in scripts, reports, exports or LLM prompts. |
| Replay state **(NEW)** | The verifier does **not** reset the target between replays. Scripts must work without a reset because they create unique data. | The planted intermittent bug (every second save fails) can only show as flaky if its counter survives between replays. |
| Sandbox | Run on the host first. Docker is a Should. | Docker problems at 3 am are the most common way to lose an hour. |
| Process | Skip the LOG.md ritual tonight. Use one shared checklist (`docs/CHECKLIST.md`), one branch per track, and merge to main every hour. | Less ceremony. The agent report at the end of each prompt replaces the log. |
